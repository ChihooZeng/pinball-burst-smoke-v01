## 二、Upper01 A/B/C

三段是**同一段波形**，只改裁剪长度与尾部淡出，不变速、不变调、不重编码音色。

| 版本 | 文件 | 时长 | 淡出 |
|---|---|---|---|
| A 原版 | `audio/clear-x14-Upper01.wav` | 3.436553s | 原始自带 |
| B 短版 | `audio/clear-x14-Upper01-short-1.35s.wav` | 1.350000s | 1.15s 起，200ms raised-cosine |
| C 中短版 | `audio/clear-x14-Upper01-short-1.80s.wav` | 1.800000s | 1.55s 起，250ms raised-cosine |

三段均为 44100Hz / 16bit / 立体声 / PCM，峰值相同（-5.51 dBFS），无削波。
**A 原文件未被覆盖**（MD5 不变），B/C 是新增文件。

波形分析结论（见交付报告）：主峰在 0.90s，之后是持续衰减的释放段；2.21–2.40s 有 190ms 的 -47dB 间隙，
2.42s 到结尾 1.02 秒基本是 -45 → -74dB 的静音尾。所以 B/C 并不损失任何独立乐句，差别只在释放段长度；
原版后 1 秒其实是听不见的静音，却让下一次清屏要等更久。

## 三、原合成提示音本轮默认关闭（可一键恢复）

`game.js` 顶部有一个开关：

```js

```

关闭的是 `playSfx()` 里由 `beep()` 生成振荡器的五个提示音：`split`（裂变）、`hunt`（追击）、
`drill`（钻头）、`arc`（电弧）、`giant`（超载冲锋 **与 Boss 降临共用**）。

- 只关播放，`beep()` 函数、五个 `playSfx("…")` 触发点全部保留，改回 `true` 即恢复，无需其它改动。
- **不会**误关四类素材音效：开关在 `PinballGameAudio.play()` 与合成音白名单之后才生效。
- 不影响 `tapHaptic()` 振动反馈。
- 审计结论：全工程只有 `playSfx → beep` 一个合成音入口；`juice-fx.js`、`builds.js`、页面均无 `<audio>` 或第二个 `AudioContext`。
- **README 旧版写的「Boss 预警」不是一个独立事件**，它就是 `bossSpawn()` 里复用的 `playSfx("giant")`，与超载冲锋同一个 beep。

## 九、V2.1h：连续击破的"杂音"修复（2026-11-10）

用户反馈：砖块击破音一旦多起来，会变成"咋一下"的爆破杂音。

**根因不是素材，是播放策略。** 原来 `cut()` 直接 `source.stop()` 硬切，而 `brick_break`
是 `cooldown 46ms / maxVoices 2`——0.16s 的样本在 46ms 间隔下最多要 3.5 层，被卡在 2 层，
于是**每来一次新击破就硬切一次旧的**。实测 24 次连续击破触发 **22 次硬切**，每秒二十几个断点，
听感就是"咋咋"的杂音。

四处修复：

| 位置 | 改动 |
|---|---|
| `cut()` | 12ms 余弦淡出后再 `stop`，不再硬切（断点消失） |
| `emit()` | 每条样本 ±6% 随机变调，避免同一条反复触发时相位对齐 |
| `emit()` | 叠音衰减 `1/(1+0.5×已响层数)`：2 层 -33%、3 层 -50% |
| `emit()` | 叠音高通：已在响时新来的那条切掉 180–900Hz 低频，只贡献瞬态，防止低频叠成轰鸣 |
| `brick_break` | `cooldown 46→62ms`、`maxVoices 2→3` |

实测对比（24 次连续击破）：

| 参数 | 硬切次数 |
|---|---|
| 旧 46ms / 2 层 | **22 次** |
| 新 62ms / 3 层 | **0 次** |

素材本身的谱平坦度（越高越像噪声）：`break-brick-e-neutral` 0.0063、`break-brick-d-deep` 0.0011、
旧 `impactGlass_heavy_000` ≈0。都不是噪声型素材，所以没有换源的必要。

## 十、V2.1i：去掉击破音的低频层（2026-11-10 09:20）

V2.1h 修完硬切后用户仍反馈"只要声音一多，还是会有爆破声"。测分频段能量后定位到素材：

| 素材 | 150Hz 以下能量 |
|---|---|
| `impactMining_002`（上一版的"石块本体"层） | **78%** |
| `break-brick-e-neutral`（合成成品） | **51%** |
| `break-brick-d-deep`（合成成品） | **75%** |
| `impactWood_light_000` | 4% |

也就是说上一版的击破音有一半以上能量是 60–110Hz 的闷轰。单条听着像"石块落地"，
一旦两层以上叠加就变成低频轰鸣——这就是"爆破声"。引擎再怎么调，素材里塞了 80Hz 的爆轰是调不掉的。

改动：

- 击破候选取掉 `impactMining` 层，换成纯中频：`BREAK-M1`（wood light 000 单层，150Hz 以下 **1%**）、
  `BREAK-M2`（wood light 002 + generic light 001，**4%**），0.11s / 0.10s
- 事件表新增 `hp` 字段，`brick_break` 设为 **200Hz 静态高通**：以后即使换回低频素材，
  这一路也会先切掉低频，不会再叠出爆破声
- 叠加时在高通基础上再抬拐点（180 + 120×层数，上限 900Hz）

实测 8 次连破：8 条都是 0.11s，高通拐点依次 200 / 300 / 300 …，0 控制台错误。

## 十一、V2.1j：击破/撞墙的"爆破声"真因——波形未从零点开始（2026-11-10 09:30）

用户对比后给了关键线索：**砖甲受击不炸，击破和撞墙炸**。

先排除电平：实测总线峰值 0.53 / 0.12 / 0.12 / 0.08，没有任何削波（`over = 0`），
且撞墙与砖甲受击电平几乎相同（0.123 vs 0.122），所以不是音量问题。

再查波形起始，找到真因：

| 文件 | 首样本值 | 结果 |
|---|---|---|
| `break-mid-wood.wav` | **-0.703** | 每次播放都是一次 0.7 的垂直台阶 |
| `wall-bounce-wood-light-000.wav` | **-0.152** | 0.15 的台阶 |
| `hit.ogg`（砖甲受击，Kenney 原文件） | -0.057 | 可忽略 |

这些文件是从素材中段直接切的，波形没有从零点开始；再做峰值归一化（0.89）时，
这个起始台阶被**放大了 4.6 倍**。每次播放等于先"啪"一下，连破时就是密集的爆破声。

修复：

- 五个文件全部做**零点对齐**（找第一个过零点，平均裁掉 0.1–1.5ms）+ **1.5ms 淡入**
- 修复后首样本全部为 0.000
- 击破增益 `.62 → .45`（归一化修正后它比砖甲受击响 3.6 倍，压到 2.7 倍）

实测总线峰值：击破 0.416 → **0.310**，撞墙 0.089，砖甲受击 0.117，清屏 0.076，全部无削波。

### 教训

生成音频时，**裁剪必须从过零点开始并加短淡入**；否则峰值归一化会把起始台阶放大成爆音。
这个问题在单次试听时几乎听不出来（就是一下"啪"），只有连续触发才暴露。

## 十二、V2.1k：素材被 force-cache 钉死，之前所有音频修复都没生效（2026-11-10 09:35）

用户"强制刷新后仍有爆破声"。检查加载策略发现：

```js
const response = await fetch(variant.url, { cache: "force-cache" });
```

`force-cache` 的语义是「只要缓存里有就直接用，不管是否过期」。而 V2.1h→V2.1j 三次修复改的都是**同名文件**
（`break-mid-wood.wav`、`wall-bounce-wood-light-000.wav`），URL 没变，所以浏览器一直在放第一次加载的旧字节。
Cmd+Shift+R 也不会绕过，因为 `fetch` 是显式读 HTTP 缓存，优先级高于强制刷新。

**也就是说 V2.1h（淡出切声）、V2.1i（去低频）、V2.1j（零点对齐）三次音频修复，用户一条都没听到。**

修复：

```js
const versioned = variant.url + (variant.url.includes("?") ? "&" : "?") + "v=" + encodeURIComponent(REVISION);
const response = await fetch(versioned, { cache: "default" });
```

- 素材 URL 带上 `?v=<REVISION>`，每次升版必然重新下载
- 缓存策略从 `force-cache` 改为 `default`

验证（持久化 profile，连续两次加载）：

```
第 1 次：break-mid-wood.wav?v=audio-qa-v21k-20261110  ✅
第 2 次：break-mid-wood.wav?v=audio-qa-v21k-20261110  ✅
```

浏览器内缓冲时长 0.1096s，磁盘文件 9710 字节（裁剪后大小），确认拿到的是新文件。
新增测试：禁止 `force-cache`、要求素材 URL 带版本号。

## 十三、V2.1m：接入背景音乐 A 组（2026-11-10 11:20）

用户听完 8 条候选后选定 A 组：**A-1 主循环 + A-2 前奏**（Future Power，作者 request）。

| 文件 | 时长 | 体积 | 用途 |
|---|---|---|---|
| `audio/bgm-futurepower-intro.m4a` | 30.24s | 590 KB | 每次开局播一次 |
| `audio/bgm-futurepower-loop.m4a` | 120.94s | 2.2 MB | 前奏结束后无限循环 |

### 处理方式（和试听版不同）

试听版给所有曲目加了 1.5s 首尾淡入淡出，对**循环曲是错的**——每轮接点会静音 3 秒。
游戏内这版重新处理：

| 项 | 循环 | 前奏 |
|---|---|---|
| 淡入 | 12ms（只防爆音） | 12ms |
| 淡出 | 12ms | **不做**（要直接接循环） |
| 响度 | -18 dBFS RMS（衰减 8.13dB） | -18 dBFS RMS（衰减 6.0dB） |
| 峰值 | 0.392 | 0.501（封顶 0.85，未削波） |
| 编码 | AAC 160k / 44.1k / 立体声 | 同 |

### 实现要点

- 用 `<audio>` **流式播放**，不走 `decodeAudioData`：两分半立体声解成 float32 要 42MB，
  手机上容易被系统回收。元素播放只缓冲流，音量走原生 `volume` 渐变（40ms 步进）。
- 元素创建后挂进 `document.body` 并设 `data-bgm="intro|loop"`，方便调试台、devtools 与自动化 inspect。
- 前奏 `ended` → 主循环 `loop=true` + 600ms 淡入接管。
- 触发点：开始游戏 `startBgm()`、触线失败 `stopBgm(1500)` 淡出、暂停 `pauseBgm()`、继续 `resumeBgm()`、重开 `stopBgm(0)`。
- 调试台新增第 8 张卡：开关、从头试听、停止、音乐音量，全部写进同一份 localStorage（`bgm: {enabled, volume}`），导出 JSON 带 `bgm` 段。
- 页面切到后台暂停、切回来恢复（不重置播放位置）。

### 实测（Chrome headless，真实鼠标点击）

| 时刻 | 状态 |
|---|---|
| 2s | intro 播放 1.97s，音量已升到 0.80 |
| 暂停 | intro 停在 4.99s |
| 继续 | 从 5.39s 接上 |
| 31s | intro 29.39s，仍在播 |
| 35s | **phase=loop，loop 播到 3.09s，intro 已 ended** |

两条 m4a 请求均 200 且带 `?v=audio-qa-v21m-20261110`，控制台 0 错误。测试 53/53。

### 已知限制

- **iOS Safari 不支持 `<audio>.volume`**（只读）。iPhone 上音乐音量滑块与淡入淡出会失效，
  音乐按元素默认音量播放。要彻底解决需改成 `createMediaElementSource` + GainNode，
  但那条路在上下文被挂起时会整条静音，风险更高，本轮未做。
- `<audio>` 循环接点在部分浏览器有几十毫秒空隙，不是采样级无缝。若听出接点问题，
  下一步改成 WebAudio 双缓冲调度。
- 技能音仍为静音（用户决定暂缓）。

## 十四、V2.1n：BGM 接入后音效听不见的修复（2026-11-10 11:40）

用户反馈：打开 BGM 后，其他音效全部没有了。

### 先测量，再下结论

在 SFX 总线上挂一个 AnalyserNode（BGM 走 `<audio>` 元素，不经过 WebAudio，
所以分析器测到的就是纯音效电平）：

| 条件 | 击破 x8 的总线峰值 |
|---|---|
| BGM 播放中 | **0.200** |
| BGM 停止后 | **0.196** |

差异 2%，可以认为完全一致 —— **音效没有被 BGM 打断，仍在正常发声**。
同时 `plays` 计数正常递增、`ctx.state === "running"`、没有静音标记。

### 真正的原因：掩蔽（masking）

| 项 | 数值 |
|---|---|
| BGM 文件 RMS | -18 dBFS（归一化后） |
| 元素音量 0.8 时 | RMS 约 **-20 dBFS**，峰值约 0.14 |
| 击破音 | 峰值 **0.2**，时长 0.11s |
| 差距 | 仅约 3dB |

音乐是**持续**的，击破是**110 毫秒的瞬态**。3dB 的差距在笔记本外放上，
瞬态会被鼓点直接吃掉 —— 听感就是"音效全没了"。

### 两层修复

1. **内部配平系数**：`BGM.trim = .45`。滑杆 100% 对应元素音量 0.45，
   而不是 1.0。原来的默认 0.8 实际变成 0.36（RMS 约 -27 dBFS，比音效低约 13dB）。
   滑杆仍然是 0–100%，用户想要大声还能自己加。
2. **战斗让位（ducking）**：任一非系统音效触发时，音乐在 90ms 内降到 55%，
   停火 420ms 后用 500ms 恢复。连发时保持压低，不会一路抖动。
   系统音（开始按钮 / 其他按钮 / 撞墙）**不触发**，避免菜单里音乐忽大忽小。

顺带修掉一个会让让位失效的 bug：`rampBgm()` 原来每次调用都重启淡入，
12.5 发/秒的连击会让 90ms 的推进被反复清零，音量实际上永远不动。
现在同一目标正在推进时直接返回，不再重启。

### 实测

| 阶段 | 音乐元素音量 |
|---|---|
| 静止 | 0.360 |
| 连破 8 次（70ms 间隔） | 0.286 → **0.198** 并保持 |
| 停火 1.5s | 回到 **0.360** |

`effectiveVolume`（实际生效音量）已加进 `getBgmState()`，调试台可查。

### 另外加的两个诊断

- `getState()` 新增 `contextState` 与 `silentDrops`：上下文不在 running 时
  被丢弃的触发会计数，不再静默消失。
- 调试台状态行显示「音频上下文 running · 因上下文未运行丢弃 N 次」。
- `startBgm()` 现在先 `setup()` 恢复上下文，再启动媒体元素 ——
  避免同一手势里媒体元素先播、把手势消耗掉导致 WebAudio 整条挂起。

测试 56/56。

### 处理：尾部 8.7 秒淡出段要裁掉

原曲从 **206 秒**开始淡出，到结尾只剩 -42 dBFS（几乎静音），最后 0.65 秒完全无声。
如果整曲循环，接点会是「安静 5 秒 + 突然炸响」，实测跳变 **28 dB**。

处理方式：
- 用 100ms 窗口 RMS 找出「最后一次仍满能量」的位置（阈值取全曲中位的一半），得到 **206.07s**
- 裁掉 8.7 秒淡出段，尾部加 150ms 淡出、头部 12ms 微淡
- 结果：尾部 -19.0 dBFS、头部 -14.3 dBFS，跳变从 **28 dB 降到 4.7 dB**

### 结构改动：支持无前奏的单曲

改动：
- `BGM.intro = null`，`bgmElements()` 只在 `intro` 非空时才创建前奏元素
- `startBgm()` 新增分支：无前奏时直接 `phase="loop"` + 播放 loop 元素
- `stopBgm()` 的 `finish()` 改成逐个元素判空 —— 否则 `intro` 为 null 时
  `els.intro.pause()` 抛错会跳过 `els.loop.pause()`，音乐停不掉
